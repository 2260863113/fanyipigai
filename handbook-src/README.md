# handbook-src：手册整理出来的中间材料

这个目录放的是《理解当代中国 核心术语学习手册》的整理结果，以及它的上游 OCR 原文。
**材料进仓库、正文一律重算**——各块 `.json` 是人工整理出来的材料，
`src/domain/terms-data/{modern-term,core-term,classics}.ts` 由 `scripts/build-handbook-terms.mjs` 从它们生成。
**不要手改那三个 .ts**（顶上写着自动生成），要改内容就改这里的 JSON，然后重跑脚本。

（为什么要有这层中转：手册是一本**扫描件**，没有可解析的文字层，机器能拿到的只有 OCR 文本；
而 OCR 有错，错必须**逐处被人判断并留下依据**，所以中间那一步不能省，也不能塞进生成脚本里。）

## 材料从哪来（整条链，照着能重做）

1. **PDF**：`笔译参考书1-《理解当代中国 核心术语学习手册》.pdf`，**166 页，扫描件、没有文字层**。
   ⚠️ **这份 PDF 不在仓库里**（167.8 MB，超过 GitHub 单文件 100 MB 上限），它一直放在用户的桌面上。
2. **逐页渲染成 PNG**（`pymupdf`，约 2 倍缩放：这是印刷体扫描件，够 OCR 用，也不至于把临时目录撑爆）。
3. **Windows OCR**（`Windows.Media.Ocr`，**这台机器上只装了中文引擎 `zh-Hans-CN`**）逐页识别，
   结果按页拼成一个文本，页分隔标记是 `===== pNNN =====`（NNN 是 **PDF 页序**，三位数）。
4. **按页切块**给整理用：每块 8 页，块边界落在三部分的范围上（见下）。
5. 每个块由一个人（代理）逐页整理成下面形状的 JSON，落在这个目录里。

**第 2、3、4 步用的是一次性脚本**（渲染用的 Python、OCR 用的 PowerShell、切块用的 Node），
它们当时放在临时目录、**没有进仓库**：脚本里写死了这台机器的绝对路径，进仓库只会误导人。
需要重做整条链时按上面四步重写即可；OCR 的唯一关键点是**只有中文引擎**——
英文是中文引擎"按字形硬凑"出来的，这正是英文错误率高的根因。

## 三部分与页范围

手册的正文分三部分，**各对应术语库里的一个板块**（见 `docs/adr/0030-handbook-terms-into-the-term-bank.md`）：

| 手册部分 | `part` | PDF 页 | 块数 | 板块 id | 每组 |
|---|---|---|---|---|---|
| 第一部分「术语英译」 | `contemporary` | p017–p059 | 6 | `modern-term` 当代术语 | 50 |
| 第二部分「术语解读」 | `core` | p061–p110 | 7 | `core-term` 必背核心术语 | 20 |
| 第三部分「用典阐释」 | `classics` | p111–p166 | 7 | `classics` 必背用典 | 20 |

**没进正文整理的两段，都是有意跳过的**：

- **p001–p016：封面、前言与**书的目录**。目录（p005–p016）本身就是一份**全部术语的索引**，
  它是**版面文字**、不是练习材料，所以一条都没收。（它现在是我们的**完整性交叉核对依据**，见下面"已经查过的事"。）
- **p060：空白扉页**（两半部分之间的隔页，OCR 出来是空的）。

⚠️ **`page` 是 PDF 页序，不是印刷页码**，两者**相差 16**（例：PDF p080 那一页印的是 64）。
块文件里的 `page` 一律写 PDF 页序，因为整理时人手边只有按 PDF 页切的块。

## 一个块长什么样

```json
{
  "part": "classics",
  "pages": "p111-p118",
  "sourceFile": "笔译参考书1-《理解当代中国 核心术语学习手册》.pdf",
  "notes": "……整理者写的订正登记与存疑登记，很长……",
  "entries": [{ "cn": "爱人利物之谓仁", "en": ["Compassion means loving and helping others."], "page": 111 }]
}
```

- `cn` 是**手册上的中文**（去掉了汉字之间的空格——OCR 会在每个汉字之间插空格），**标点照原样保留**（含句末「。」）。
- `en` 是**手册给出的英文译法**，一条术语可能有多条（书里就是这么给的）；`en` 为空数组表示手册没给可读的译法。
- `notes` 是**这个块最重要的东西**：逐处登记「OCR 原样 → 订正（依据）」，以及「存疑」。审计看的就是它。

## 各部分的抽取规则（三部分版式不同，规则也不同）

1. **第一部分「术语英译」**：双栏，左栏中文术语、右栏英文译法。**两栏行数常常不等**
   （一条中文对应两三条英文译法、一条英文被 OCR 折成两三行），因此配对**必须按语义**，绝不按行号。
   整理者被要求**逐页做条数对账**（中文条数 vs 英文条数，差额必须全部由"一条多译"解释得通），
   这是"没有整条错位"的硬证据。
2. **第二部分「术语解读」**：一页 1–3 条，版式是「中文术语行 → 项目符号的英文译法」，
   后面跟整段中文解读与整段英文解读。**只要术语与译法，两段解读一律不要**（用户的口径）。
   ⚠️ 这一部分的坑是：**页首常常先是上一条术语的英文解读尾部**，极易被当成新术语的译法。
3. **第三部分「用典阐释」**：版式是「中文典故行 → 项目符号的英文译法（1–3 条）→ 中文出处解释（出自…意思是…）→ 成段英文阐释」。
   **只要「中文典故 + 英文译法」**，出处解释与英文阐释都不要。
   ⚠️ 这一部分的坑同样是**页首的英文是上一条的阐释续段**。

页眉也要认：奇数页印「用 典 阐 释」、偶数页印「第 三 部 分」（第一、二部分同理），
**页眉交错是装帧习惯，不是越界**；反过来，凡出现下一部分的部分名，就是越界，该停。

## OCR 的成色（决定了这批数据的可信度上限）

- **中文**：好。主要问题是每个汉字之间插了空格（一律去掉），以及少量形近误识（`夭`↔`天`、`斡`、`氵齐`、`亻木`、`弓虽` 之类），整理者逐处订正并写依据。
- **英文**：约 **6%** 是错的，四类为主：① 句中虚词被识成大写（`Of` / `tO` / `aS`）；② 单词被空格劈开（`ta lent`、`Thoug ht`）；③ 字形互串（`0`↔`o`、`l`↔`I`、`m`↔`rn`、`tit`↔`t`）；④ 整词乱码（`丨 OS 巳` → `lose.`）。
- **最危险的不是乱码，是配对错误**：一个看不懂的乱码读者会怀疑，而一条**通顺却属于别人**的英文，
  读者会当成官方译法背下去。因此整理者被要求专门做**配对自检**，并把拿不准的写成 `存疑（配对）`。

## 两条硬规矩（整理时对每个块都交代过）

1. **英文只能来自 OCR 原文**：不许自译、不许凭常识补词。实在缺词/残缺，就**保留原样**并写进 `notes` 的存疑登记。
   一个例外是**修订**：形近误识、拆词、大小写这类"同一个词的另一种写法"必须订正（`tO`→`to`），但**每一处都要写依据**。
2. **中文条目只去字间空格，标点原样**：不替手册改标点，也不删句末句号。

## 已经查过的事（进来的审计看这几条，别重复劳动）

- **`scripts/build-handbook-terms.mjs` 的四项体检**（条数 / 页对应 / 重复 / 英文里的 OCR 残留字形）：全部通过，现在 858 条。
  - 「页对应」= 每条 `page` 必须落在本块自己的页范围里；「重复」= 同一部分内不许有重复中文条目（**跨部分允许**，见下）。
- **跨板块重复 59 条是原书体例，不是数据错**：第二部分讲的就是第一部分里最该背的那些术语，
  所以同一术语在两个板块里各出现一次。59 而不是 60，是因为第二部分那条写作「落实“六稳”任务」、
  第一部分写作「落实“六稳”“六保”任务」，字符串不同。两条在各自板块里出的题不同（第二部分的解读是它的重点）。
- **印刷目录的完整性交叉核对**：把 p005–p016 的目录 OCR 文本与 858 条对上——目录里能认出来的术语
  **没有一条是资料里缺的**（对不上的那些全是目录折行与 OCR 错字造成的假阴性，逐条查过）。
- **独立配对审计（已做完）**：另有一份**不读整理者 `notes`、只回 OCR 原文**的抽样审计——
  20 个块分层抽样 **159/858 = 18.5%**（第一部分 10%、二/三部分 60%），逐条回页判定，
  结果 **OK 156 / 存疑 3 / 错配 0**：**没有发现一处中英配错**（"存疑"那 3 条是英文残缺，不是配错）。
  它还把 22 处自报「存疑（配对）」展开成的 45 条实质疑点逐条回页复核，结论同样是
  **配对口径应改 0 处**。按 0/159 估（rule of three），第一部分未抽到的 645 条里错配的上界约 4%——
  所以结论是"**抽到的都对 + 明确的上界**"，不是"绝对没有错配"。
- **跨板块一致性**：59 条在两个板块里重复的术语，两边算对集合现在 **58 条完全相同**，剩下 1 条
  （`中国式现代化`）是两边**印法本身不同**（`Chinese path to modernization` 与
  `Chinese (path to) modernization`），生成器把后者的括号展开、前者照样算对，因此不冤枉人。
- **一英多中**：这 59 条里有一对是**真正的一英多中**——`落实“六稳”“六保”任务`（第一部分）
  与 `落实“六稳”任务`（第二部分）英文是同一条 `to stabilize the Six Fronts and guarantee the Six Priorities`。
  生成器按 `build-terms.mjs` 同一口径把两者互相登记进 `zhAlt`，英译中方向下写哪个中文名都算对。

### 判分上的一处放宽：手册写在纸面上的并列写法

手册用两种记号把"同一个答案的几种写法"直接印在行里：**括号表示可省略**
（`Chinese (path to) modernization`）、**斜杠表示并列可选**（`a new form/model/type of international relations`）。
照着字符串比会**冤枉照另一处写法作答的人**（用户照第一部分那一版写 `Chinese path to modernization`，
在第二部分那边会被判错）。因此生成器把这两类记号展开成"也算对"的写法放进 `enAlt`
（现在 41 条译法展开出 88 种写法），**屏幕上显示的标准答案仍是手册印的那一串**。

它属于既有的「同一个答案的不同写法」放宽（官方缩写、英美拼写那一类），**不是同义替换**：
`whole-process people's democracy` 与 `whole-process democracy` 仍然只认前者。
展开逻辑在 `scripts/build-handbook-terms.mjs` 的 `printedVariants()`。

## 怎么重新生成数据

```bash
node scripts/build-handbook-terms.mjs            # 体检：只报告，不写文件
node scripts/build-handbook-terms.mjs --write    # 写进 src/domain/terms-data/
```

体检查出问题（页对应不上、同部分内重复、英文里还有 `tO`/`0f`/全角标点这类残留）时**拒绝写文件**，
这是有意的：宁可让生成器停下，也不要把一处明显还没订正的字写进术语库当标准答案。

生成之后还要跑 `scripts/check-terms.mjs`（术语库结构与分组的体检）与 `npm run smoke`。
改数据一定会动到的两处**平行登记**：`src/domain/term-scopes.ts` 里 `TERM_SCOPES` 的 `perGroup`
（本脚本里的 `PARTS` 表也写了同一个数，两处必须一致）。
