# 英译中·精修改成五遍自查；漏译按字数扣分

这一条记两件事，它们是同一批里一起定的（用户第 13、14 条），而且**互相牵连**：
漏译被提到第一遍去查，同时它的扣分方式也换了。

## 一、英译中·精修：五遍自查（第 14 条）

用户的原话：

> 对于英译中的精修批改，更新提示词，要求先检查"漏译"（前端处理：两个及字以内算作橙色，
> 三个字及以上算作红色，扣分按照遗漏字数算），再检查"术语错误"（错一个字就标红），
> 再检查"啰嗦部分"（橙色），再检查"更好的表达""更好用词"（橙色）。

追问"你列的四遍里没有语法与标点，怎么办"时，他选的是**五遍**：
**漏译 → 术语 → 啰嗦 → 更好的表达/用词 → 语法与标点**（语法与标点排最后，但**仍然查**）。

于是提示词里"分几遍自查"那一节变成**按方向分叉**（`prompt.ts` 的 `PASS_PLANS`）：

| | 英译中·精修 | 中译英·精修 |
| --- | --- | --- |
| 遍数 | 5 | 4（**没变**） |
| 顺序 | 漏译与多译 → 术语 → 啰嗦 → 更好的表达/用词 → 语法与标点 | 语法/标点 → 漏译与多译 → 术语 → 表达（含啰嗦） |

⚠️ 用户明确说"**只给英译中**"，因此中译英仍是老口径。代价是两个方向的批改风格不完全一致
（同一个错误在哪一遍被查到不一样），这一点是他知情的取舍。

### 两个必须一起改的连带

- **「啰嗦」是一个新分类**（`verbosity`，橙色/表达问题）。它进的是**共享的分类表**，
  因此两个方向都能用它——中译英那一档把它并进"表达是否地道"那一遍，不单列一遍。
- **"检查顺序"与"归类优先级"必须分开说**。老提示词里这两件事是同一件（"优先级从高到低
  就是 1→2→3→4"）。现在检查顺序把语法排到最后，如果继续说"按遍数定优先级"，
  一处既啰嗦又语法不通的地方就会被归成"啰嗦"（橙）——那正是老提示词反复警告的错。
  因此新文本里写明：**归类仍然按分类表的顺序，硬性错误（红）优先于表达问题（橙）**。

## 二、漏译按字数扣分（第 13 条）

用户的原话："漏译的扣分单独算，按照漏多少字（单词），扣多少分。"
追问"与原来的每处固定分是什么关系"时，他选的是**完全按字数扣、不再另扣固定分**：
漏 20 个字就扣 20 分。

于是算分变成三种扣法并存（`scoring.ts`）：

| 什么 | 怎么扣 |
| --- | --- |
| 漏译（`omission`） | **每个单位扣 1 分**（中译英数词、英译中数汉字）——与"轻重按字数判红橙"同一套单位 |
| 其它硬性错误 | 每处扣 8 分 |
| 表达问题 | 每处扣 3 分 |

三条配套的规矩：

1. **图例里的处数照旧把漏译算在内**（`hardCount`/`softCount`）。漏译在页面上也会被标红或标橙，
   图例少算它就会变成"标了 5 处红、图例说 3 处"——本项目最不想要的就是这种自相矛盾。
   算分时它被单独拿出去按字数扣，两件事因此各归各。
2. **分数栏单独写一行**：「漏译扣 X 分（漏 N 个单位）」。不写出来的话用户只看到一个总数，
   而"漏多少扣多少"是他自己定的规矩，必须能核。
3. **多译（`addition`）仍按"每处"扣**——他只点名了漏译。真要与漏译对齐（按多出的字数扣），
   `scoring.ts` 里留了一处开关说明；改之前先问，不替他决定。

## 与 ADR 0014 的关系

ADR 0014 定的是"四遍自查 + 漏译/多译的**轻重**由程序按字数判"。这一条：
- **推翻**了它的"四遍"（英译中改成五遍）与"漏译按红/橙扣固定分"（改成按字数扣）；
- **保留**了它最核心的那条：**红还是橙由程序按字数判、不问模型**（`severity.ts` 一个字没动，
  门槛仍是"1–2 个单位橙、3 个及以上红"）。

## 代价

- 一句话里的漏译很容易把分数压到很低（漏 30 个字就是 −30）。这正是用户要的"漏多少扣多少"；
  但若以后想加"漏译扣分上限"，改 `OMISSION_PENALTY_PER_UNIT` 与那一条说明即可。
- 两个方向的自查遍数不同，维护提示词时**要记住只改英译中的那一半不要顺手改另一边**。
  `smoke` 里有断言盯着两边（`走 5 遍` / `走 4 遍`、第 N 遍查什么），改错会当场变红。
