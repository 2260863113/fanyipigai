# 批改分四遍自查，漏译/多译的轻重由程序按字数判

用户对"怎么批"给了两条硬口径：

1. **分四遍自查、每遍专攻一类错误**，优先级从高到低：语法（冠词、时态、单复数、介词、主谓一致、
   句子结构）→ 漏译与多译 → 专有名词与术语 → 表达是否地道。同一处文字同时像两类错误时，
   只算优先级高的那一类。
2. **漏译/多译的红橙由程序按字数判**："漏 0~2 个单位算橙色，漏三个单位以上算红色。"

## 四遍只是提示词里的自查方法，**不是四次请求**

澄清一下措辞：这是用户明确选的——"只发一次请求，提示词里要求它分四遍自查"。
理由很实际：真发四次请求会把**花费与耗时都乘以四**（实测一次约 0.034 元、10–35 秒，
一页就会变成约 0.14 元、40–140 秒），而收益只是提示词更聚焦。
代价是"四遍"只是模型的自律，程序验不了它真的走了四遍——这一点如实记在这里。

## 标点、语序、亮点各归哪一遍（现有十个分类要分完）

用户列的四类盖不住原有分类，三处由用户定了归属：

| 分类 | 归哪一遍 | 颜色 |
| --- | --- | --- |
| grammar / function-word | 第 1 遍（语法） | 红 |
| punctuation | 第 1 遍（语法） | 红 |
| omission / addition | 第 2 遍（漏译多译） | **按字数定** |
| terminology | 第 3 遍（术语） | 红 |
| word-order / collocation / word-choice / register | 第 4 遍（地道） | 橙 |

**亮点只由第 4 遍给**：前三遍是在挑错，正面的判断放到最后一遍一起说，
免得同一句好话被四遍各夸一次。

## 按字数判轻重：单位取**译文那一侧**（最容易搞反）

"漏掉的那段文字活在译文里"，所以量它要用译文那一侧的口径：
中译英的译文是英文 → 数**词**；英译中的译文是中文 → 数**汉字**。
这与文章篇幅的口径（原文那一侧）**恰好相反**，实现里是把方向翻过来再交给 `countUnits`
（见 `domain/severity.ts`）。

为了让程序量得准，提示词里加了两条硬性要求：**漏译一律用 insert 表达、多译一律用 delete 表达**，
且 `targetText` / `oldText` 里只放漏掉/多出的那部分。写成整句重写就量不出来了。

## 颜色不再只由分类推导（这条改动的真正代价）

本项目原来的口径是"颜色由分类推导，不由模型选"——同一类错误每次都是同一个颜色。
漏译/多译现在**同类不同色**，因此：

- 颜色的**唯一来源**变成解析时算好的 `ValidatedError.hard`（下游排版、对照视图、说明卡片都读它）；
- `colorForCategory` 退化成"只认分类"的那一面，只用在图例上（并标注"按字数定红/橙"）；
- `scoreCorrection` 多收一个 `direction`——分数必须与页面上标的颜色同源，否则会出现
  "标着橙却按红扣了 8 分"。
