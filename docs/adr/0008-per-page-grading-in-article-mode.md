# 文章题逐页批改：一页一页译、一页一页交，结果按页存

文章题（一篇多页的那种）不再"整篇写完再一次性提交"。现在是一页一页走：点「下一页」时，**刚写完、还没批过**的那一页自动交去批改；已经批过的页翻回去只看结果、不重新提交；被「返回编辑」放开改过的页不会再自动提交。批过的页是**只读**的，想改要先按「返回编辑」。

## 四条规矩，以及每条为什么这么定

1. **离开一页时自动提交那一页。** 用户的动作是"写完这一页，翻到下一页接着写"，提交夹在中间符合直觉；不这么做就只能靠用户每页手动按一下，忘一次那一页就静悄悄没批。
2. **批过的页翻回去不重新提交。** 批改要十几秒、还可能给出与上次不一样的结果；用户翻回去只是想**看**当时批了什么。
3. **批过又被放开改过的页，绝不自动提交。** 放开意味着"我要改这一页"，改成什么样还没定；这时替他交一次等于白花一次调用，而且他后面接着改，交出去的那份立刻就作废了。改完由他自己按「提交批改（手动）」。
4. **批过的页只读。** 批注的位置是按**提交当时**那段文字算出来的，改一个字就全对不上了。所以先只读，由用户明确说一句"我要改"（按「返回编辑」）才放开——那一刻结果作废、草稿留着。

## 为什么结果必须按页存

第一版里一道题只有**一个** `result`（"上一次的批改"）。逐页批改下它立刻不够用：翻到第 4 页提交会把第 2 页的结果冲掉，用户再翻回去就只能重新提交一次（十几秒、还可能是另一份结果）。

因此会话状态里改成 `pages: 页号 → { 草稿, 提交当时的那段文字 }`：

- 存**提交当时的那段文字**（`answer`）而不是只存批改，是因为**批注与计分必须对着被批的那一版**；用户后来改过的草稿只能用于"这一页是不是改过"这个判断，不能拿去渲染批注。
- 顺带**删掉了 `view`（看作答还是看结果）这个状态**：它由"这一页有没有结果"推出来就够了。两份状态迟早会打架——第一版就有过：`view` 说在看结果，而结果已经被换页清掉了。

## 为什么"改动作答"不再作废旧结果

作废只发生在**「返回编辑」那一下**。如果"打字"也顺手作废，就分不清两种状态：

- 这一页**从没提交过** → 翻页时**应该**自动提交；
- 这一页**提交过、现在被改过** → 翻页时**绝不能**自动提交。

这两种情况的界面上长得一样（都有文字、都没有结果），差别只在"曾经有没有被放开过"，因此它必须是一个**显式记住**的状态（`unlocked`），不能靠推断。

> ⚠️ 这里我自己写错过一次：`pageState` 最初写成"有结果且未被放开过 → 已批改，否则待批改"。可是「返回编辑」已经把结果作废了，于是放开之后这一页落回"待批改"，又被当成没批过的页 → 翻页时自动提交（正是第 3 条要禁止的），界面也永远不承认"这一页改过"。教训：**三态互斥的判据要按"谁最先成立"排序，别让派生条件盖住显式状态。**

## 一次提交批的是哪一页，必须在发请求之前钉死

`commit()` 接收调用方在**发请求之前**取好的目标（题号 + 页号），不读外层的 `session.sectionIndex`。批改要十几秒，这期间用户完全可能翻页、甚至切到别的题；那样结果会被记到**别人头上**——而界面上完全看不出来（分数与勾画都长得对）。

## 练习记录：一条记录 = 一页

逐页批改之后，`answer` 的含义从"整篇"变成"一页"，因此记录里新增了必填的 `sectionIndex`，存储键升到 `records.v2`：v1 里一条是整篇、v2 里是一页，混着读会让界面**理直气壮地显示对不上的东西**（比丢掉更糟）。用户明确说"已有的旧记录直接作废"，v1 那份留在浏览器里不动——不主动删别人的数据。

## 放弃的东西

- **"整篇一起批"这条路径没有了**（连带"按段并行批改"在文章题上也不再触发）：一次只批一页，所以篇与篇之间的风格一致性不如从前。换来的是每一页都能单独回看、单独重批。
- **成本结构变了**：一篇 8 页的文章现在是 8 次调用（每次更短），而不是 4 次并行的长调用。总量接近，但**用户翻页的动作会真的花钱**——这正是第 3 条规矩存在的原因。
